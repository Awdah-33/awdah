# خطة التشغيل والدعم
## منصة رجعة | Rajaa

## 1. الهدف

تهدف هذه الوثيقة إلى تنظيم تشغيل منصة رجعة بعد الإطلاق، وضمان:

- استقرار النظام
- سرعة معالجة المشاكل
- حماية البيانات
- استمرارية الخدمة
- وضوح مسؤوليات الفريق
- تقديم دعم مناسب للعملاء

---

## 2. قنوات الدعم

القنوات المقترحة:

- WhatsApp Business
- البريد الإلكتروني
- نظام تذاكر دعم داخلي مستقبلًا

في البداية يمكن الاعتماد على:

- WhatsApp
- Email

مع توثيق كل مشكلة مهمة.

---

## 3. تصنيف طلبات الدعم

### Critical

مشكلة توقف النظام أو تسبب:

- فقدان بيانات
- خطأ مالي كبير
- كشف بيانات بين مغسلتين
- توقف تسجيل الغسلات بالكامل

الأولوية:

فورية.

---

### High

مشكلة تؤثر على وظيفة أساسية مثل:

- الفواتير
- الولاء
- تسجيل العملاء
- تسجيل الغسلات

---

### Medium

مشكلة مهمة لكن يوجد بديل مؤقت.

مثل:

- تقرير لا يعمل بشكل صحيح
- فلتر لا يعمل
- مشكلة في واجهة معينة

---

### Low

مشكلة بسيطة مثل:

- تنسيق
- ترجمة
- محاذاة
- تحسين تجربة المستخدم

---

## 4. التعامل مع الأعطال

عند حدوث مشكلة:

1. تسجيل المشكلة
2. تحديد مستوى الخطورة
3. تحديد العميل المتأثر
4. تحديد وقت بداية المشكلة
5. محاولة إعادة المشكلة
6. تحديد السبب
7. إصلاح المشكلة
8. اختبار الإصلاح
9. نشر الإصلاح
10. التأكد من عودة النظام للعمل
11. توثيق السبب والحل

---

## 5. الأعطال الحرجة

في حالة Critical Incident:

يتم التركيز أولًا على:

- حماية البيانات
- منع توسع المشكلة
- إعادة الخدمة
- منع التكرار

إذا لزم الأمر:

يتم إيقاف وظيفة معينة مؤقتًا بدل المخاطرة بالبيانات.

---

## 6. Rollback

كل إصدار Production يجب أن يسمح بالرجوع إلى الإصدار السابق عند حدوث مشكلة خطيرة.

قبل كل نشر:

يجب التأكد من وجود:

- نسخة من الإصدار السابق
- Database Migration Plan
- Rollback Plan

---

## 7. النسخ الاحتياطية

يجب إنشاء Backup دوري.

الاقتراح:

- Backup يومي
- الاحتفاظ بعدة نسخ
- نسخة خارج الخادم الأساسي

ويجب حماية النسخ الاحتياطية.

---

## 8. اختبار الاستعادة

وجود Backup لا يكفي.

يجب اختبار Restore دوريًا.

الهدف:

التأكد من أن النسخة:

- سليمة
- قابلة للقراءة
- يمكن تشغيل النظام منها

---

## 9. المراقبة Monitoring

يجب مراقبة:

- حالة API
- Database
- Queue
- Redis
- Server Resources
- الأخطاء
- أوقات الاستجابة

---

## 10. Health Checks

يجب وجود Health Check للخدمات الأساسية.

مثال:

- Backend يعمل
- Database متصلة
- Redis يعمل
- Queue يعمل

---

## 11. Error Monitoring

يتم تسجيل أخطاء النظام بشكل مركزي.

ويفضل استخدام خدمة مثل:

- Sentry

أو حل مشابه.

الهدف:

معرفة:

- مكان الخطأ
- المستخدم المتأثر
- الوقت
- عدد مرات التكرار

---

## 12. Metrics

يتم قياس مؤشرات مثل:

- عدد الطلبات
- معدل الأخطاء
- سرعة API
- عدد الفواتير
- عدد عمليات الغسيل
- استخدام قاعدة البيانات

---

## 13. التنبيهات

يجب إرسال Alert عند:

- توقف API
- ارتفاع نسبة الأخطاء
- فشل Backup
- امتلاء مساحة التخزين
- مشاكل قاعدة البيانات
- توقف Queue Worker

---

## 14. إدارة الإصدارات

يجب أن تكون الإصدارات منظمة.

مثال:

- v1.0.0
- v1.0.1
- v1.1.0

ويتم تسجيل التغييرات في:

CHANGELOG.md

---

## 15. أنواع الإصدارات

### Patch

إصلاح أخطاء بسيطة.

مثال:

v1.0.1

### Minor

ميزة جديدة لا تكسر النظام الحالي.

مثال:

v1.1.0

### Major

تغيير كبير.

مثال:

v2.0.0

---

## 16. بيئات النظام

يفضل وجود:

### Development

للتطوير.

### Staging

للاختبار قبل الإنتاج.

### Production

للعملاء الحقيقيين.

لا يتم اختبار الميزات الجديدة لأول مرة على Production.

## 19. الصيانة

يتم تنفيذ الصيانة عند الحاجة.

يفضل:

- خارج أوقات الذروة
- إعلام العملاء مسبقًا إذا كان هناك توقف

---

## 20. تحديثات الأمان

يجب متابعة تحديثات:

- Laravel
- React
- PostgreSQL
- Redis
- Docker
- نظام التشغيل
- Dependencies

ويتم تطبيق التحديثات الأمنية المهمة بسرعة.

---

## 21. إدارة الثغرات

عند اكتشاف ثغرة:

1. تقييم الخطورة
2. تحديد الأنظمة المتأثرة
3. تطبيق إصلاح
4. اختبار الإصلاح
5. نشره
6. مراجعة Logs
7. توثيق الحادثة

---

## 22. حادث أمني

إذا حدث Security Incident:

يتم:

- منع الوصول غير المصرح
- حفظ الأدلة
- تغيير Credentials عند الحاجة
- تحديد البيانات المتأثرة
- إصلاح السبب
- متابعة النظام
- توثيق الحادثة

---

## 23. الصلاحيات الداخلية

حتى فريق رجعة يجب ألا يحصل جميع أفراده على وصول كامل.

يتم تطبيق:

Least Privilege

أي:

كل شخص يحصل فقط على الصلاحيات التي يحتاجها.

---

## 24. الوصول إلى Production

الوصول إلى Production يجب أن يكون محدودًا.

يفضل:

- حسابات منفصلة
- MFA
- Audit Logs
- عدم مشاركة كلمات المرور

---

## 25. الأسرار Secrets

لا يتم وضع:

- كلمات المرور
- API Keys
- Database Credentials

داخل GitHub.

يتم استخدام:

Environment Variables

وSecret Management.

---

## 26. خدمة العملاء

عند استقبال مشكلة من مغسلة:

يجب تسجيل:

- اسم المغسلة
- الفرع
- المستخدم
- وقت المشكلة
- الخطوات التي حدثت
- صورة أو فيديو عند الحاجة
- رقم الفاتورة عند وجودها

---

## 27. قاعدة المعرفة

يتم إنشاء Knowledge Base تحتوي على:

- طريقة إضافة عميل
- طريقة إضافة سيارة
- تسجيل غسلة
- إلغاء فاتورة
- إدارة الموظفين
- التقارير
- إعدادات الولاء

الهدف:

تقليل الحاجة للدعم المباشر.

---

## 28. تدريب العملاء

يفضل أن يكون التدريب قصيرًا.

صاحب المغسلة:

- Dashboard
- التقارير
- الإعدادات
- الموظفون

الموظف:

- العملاء
- السيارات
- تسجيل الغسلة
- الفواتير

---

## 29. Onboarding

عند اشتراك مغسلة جديدة:

1. إنشاء الحساب
2. إضافة بيانات المغسلة
3. إضافة الفروع
4. إضافة الخدمات
5. إعداد الأسعار
6. إعداد الولاء
7. إضافة الموظفين
8. تدريب سريع
9. تنفيذ عملية تجريبية
10. بدء التشغيل

---

## 30. قياس الدعم

مؤشرات مهمة:

- عدد التذاكر
- زمن أول رد
- زمن حل المشكلة
- عدد المشاكل المتكررة
- عدد المشاكل Critical
- رضا العميل

---

## 31. المشاكل المتكررة

إذا تكررت نفس المشكلة أكثر من مرة:

لا يتم الاكتفاء بحلها لكل عميل.

يجب البحث عن:

- السبب الجذري
- تعديل المنتج
- تحسين الواجهة
- تحسين التوثيق

---

## 32. Root Cause Analysis

للأعطال المهمة يتم كتابة:

- ماذا حدث؟
- لماذا حدث؟
- كيف تم اكتشافه؟
- كيف تم إصلاحه؟
- كيف نمنع حدوثه مرة أخرى؟

---

## 33. تحديث قاعدة البيانات

أي Database Migration يجب أن تكون:

- موثقة
- مجربة على Staging
- لها Backup
- قدر الإمكان قابلة للتراجع

---

## 34. التعامل مع البيانات

يجب عدم تعديل بيانات العملاء مباشرة في قاعدة البيانات إلا عند الضرورة.

يفضل أن تتم التعديلات عبر:

- Admin Tools
- Scripts موثقة
- API

مع Audit Log.

---

## 35. الأداء

عند وجود بطء:

يتم فحص:

- Database Queries
- Indexes
- Cache
- API
- Server
- Network

قبل زيادة موارد الخادم مباشرة.

---

## 36. التوسع

عند زيادة عدد المغاسل:

يمكن التوسع عبر:

- زيادة API Instances
- زيادة Queue Workers
- تحسين Database
- Redis
- CDN
- Load Balancer

---

## 37. الاستمرارية

الهدف أن تكون رجعة خدمة يمكن الاعتماد عليها يوميًا.

لذلك:

- لا يتم نشر تغييرات خطرة بدون اختبار
- لا يتم حذف بيانات بدون سبب
- لا يتم تغيير قواعد الولاء بدون توثيق

---

## 38. مسؤولية فريق رجعة

فريق رجعة مسؤول عن:

- استقرار المنصة
- الأمان
- النسخ الاحتياطية
- إصلاح الأخطاء
- تحديث النظام
- الدعم التقني

---

## 39. مسؤولية المغسلة

المغسلة مسؤولة عن:

- صحة بيانات الموظفين
- الحفاظ على حساباتها
- عدم مشاركة كلمات المرور
- مراجعة الأسعار
- الإبلاغ عن المشاكل
- استخدام النظام بطريقة صحيحة

---

## 40. حدود الدعم

دعم رجعة يشمل:

- مشاكل النظام
- الحسابات
- الفواتير
- الولاء
- الصلاحيات
- التقارير
- مشاكل الاستخدام

ولا يشمل مثلًا:

- مشاكل إنترنت المغسلة
- أجهزة شخصية تالفة
- خدمات خارجية لا تتحكم بها رجعة

إلا بقدر المساعدة الممكنة.

---

## 41. معيار نجاح التشغيل

يعتبر التشغيل ناجحًا عندما:

- النظام مستقر
- المشاكل الحرجة نادرة
- النسخ الاحتياطية تعمل
- الاستعادة تم اختبارها
- الدعم سريع
- العملاء يستطيعون العمل يوميًا بدون تعطيل

---

## القاعدة الذهبية

في التشغيل:

**الاستقرار والأمان أهم من سرعة إضافة المزايا الجديدة.**

---

## الخلاصة

تشغيل رجعة يجب أن يعتمد على:

- Monitoring
- Backups
- Security
- Support
- Documentation
- Testing
- Controlled Deployments

حتى تصبح رجعة منصة يعتمد عليها أصحاب المغاسل في عملهم اليومي.
